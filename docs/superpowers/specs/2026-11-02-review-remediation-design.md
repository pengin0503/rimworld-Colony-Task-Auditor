# Colony Task Auditor 1.1.x レビュー是正・軽量化設計
> 2026-11-02 / planning only / implementation not started
> 基準 main `726c2c8206d4cfc5c0038d5de41262ebb16bf103`
> 既存仕様 `docs/superpowers/specs/2026-11-02-actionable-automation-design.md`

## 目的・境界
Issue #25–#30の修正・機能改善・軽量化を行い、重要作業の監視の公平性と手動操作尊重を守る。既存3 MODの旧機能はユーザーがプレイ確認済み。**今回の新たな自動化機能の通常プレイ、セーブ/ロード、270+MODでのTPSは別途未確認**で既存 #7 に記録。安全でない自動Job/恒久的な優先度書換えを追加しない。実装外の拡張、他リポジトリ・テストホストの修正をしない。

## 設計方針（Issue別）
1. **#28 優先作業Set/Clearの所有権判定（先行）:** `TaskPriorityHooks.ExternalWrite`はMOD自身が明示実行した書込み以外のSet/Clearで`watch.AutoAssist=false`。バニラの自然完了やエンジン側のClearも通る可能性があり、**ここは仮説のため実物DLL呼出元と実ゲームで確認してから修正する**。プレイヤー/他MODの同一tick・同一内容Set/Clearを尊重し、正常終了は自動権限を無意味に失わせない。区別できないときは手動書込み保護を優先し、誰がいつ何を変えたか履歴に記録。永続の優先度やJobを復元/強制しない。
2. **#25 重要作業の公平な巡回:** `Watches.Take(4)`と`Where(AutoAssist).Take(4)`は先頭に固定される。重要作業5件以上が登録されたとき、5件目以降のAuto準備が永続に飢餓しないよう、保存/復元できるround-robinカーソルで監視・Ready証明・通知を公平に巡回する。現在の1スキャンあたりのProofBudget=64、最大4監視対象/各候補8人、250/5000Tickスケジュールは維持。検証できなかった対象をReadyとはしない。進捗クロックのリセットと誤通知を避ける。
3. **#26 監視と作業支援の独立:** `TaskWatchlist.Threshold(w,ordinary,AssistanceMode)`の結合を分離し、AssistanceMode OffでもWatch登録された重要作業にはその閾値が反映される。必要なら監視機能自体のOffを独立追加。ただし旧セーブで旧警告が無断で増加しない移行方法を用意。監視のオン/オフと書込み権限を混同しない。
4. **#29 詳細の鮮度:** `Window_TaskRemedy`はConfirm時にUI詳細更新が止まる。画面の描画中に`audit.Scan()`を毎フレーム呼ばず、`LastScanTick`変化で既存の記録/コンテキストから詳細だけ更新し、候補Previewを破棄。対象消失・作業完了・設定変更時は明確な状態表示とし、実行直前は従来どおり最新の証明を取り直す。
5. **#27 原因別の具体的行動:** 現行の`TaskRemedyPlanner`は`CTA_Ready`以外`CanExecute=false`。診断表示とWorkタブ移動はあるが、原因別の具体的な安全操作は乏しい。優先度は (a)材料不足なら不足品名/保管場所/対応作業台・製造指示への誘導、(b)作業者不足なら対応する入植者の選択と作業設定画面への誘導、(c)制限/技能/到達不能は検証根拠を明示して関連対象へ誘導、(d)危険な自動解除は実装しない。**提案/ナビゲーションと、実際に世界を変更する操作を区別**し、変更操作は確認付き・許可・対象の再確認が可能な場合のみ。改修が新たな危険なAutoを暗黙許可しない。
6. **#30 大規模マップ性能:** `TaskAuditor.ScanCore`は毎スキャン全`AuditRecord`複製・再ソート・辞書再構築を行い、`TaskDetails.Inspect`で線形探索、`TaskAuditListView`で非表示行も反復。まず現行と修正の負荷を比較し、安定性を崩さない索引利用・表示可視範囲絞り・差分スナップショット再利用を検討する。進捗クロック・安全な旧Record保持・PartialScan・回転カーソルに影響しない範囲から着手。効果が測れない大規模書換えはしない。

## 変更の境界・安全性
- 一時作業支援は**バニラPriorityWorkだけ**、既存の`IdleSafe`、Danger.None、スキャナでの実Job可能性、マップ同一性・現在のWorker/WorkGiverの確認を保つ。徴兵・医療・消防・救助・手動Jobを割り込ませない。
- 原因が`Unknown`、PartialScan、古いRun、指定WorkGiverが不明、他優先度管理MODの競合がある場合、Auto介入なし。
- ユーザー手動Set/Clearが同一tickの同値でも優先。外部書込みを認識した管理項目を勝手に元に戻さない。
- 重要作業監視のWatchと作業支援権限`AutoAssist`は別。Watchが切れた場合は一時指示の次の解除時刻まで整合性を保つ。
- 日本語・英語は同等、保存対象のID・Map ID・時計・カーソルは旧セーブから安全に初期化。
- RimWorld 1.7 API索引 `research/vanilla-1.7.4985/` とDLL実物を照合。特に`PriorityWork.Set/Clear`の呼び出し主体を確定せずに責任を断定しない。
- `RimWorld-for-mod-test`は必須でない。公開CIは純モデル/ビルド/翻訳/パッケージを実行、実ゲーム動作を偽装しない。

## 代替案と採用
- **監視:** 上限を単純に100へ増加→不採用（スキャン・Job証明の負荷増大）。上限は固定して公平に巡回→採用。
- **優先支援:** 手動操作の検出を外す→不採用（同一tickの上書きを防げない）。呼出元・状態に基づく分類、曖昧なら安全側停止→採用。
- **解決アクション:** 汎用Job強制・作業表数値書換え→不採用。原因別のナビゲーションと限定確認付き操作→採用。
- **性能:** すべてを新しいECS/スレッド化→不採用。計測・辞書再利用/仮想スクロールなど局所的な等価最適化→採用。

## 完了ゲート
#25–#30をすべて再現テストまたは仕様確認で証拠付けし、CIと必要なコンパイルが成功。#28は実物呼出経路/実ゲームの根拠が得られなければ安全側の保護を維持し未確定と記録する。#30は性能前後実測を残す（実測できなければ効果未確認）。新たな自動化のゲーム内受入はIssue #7にまとめ、重複Issueを作らない。
